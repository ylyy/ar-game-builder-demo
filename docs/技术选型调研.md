# 摄像头驱动游戏角色 — 技术选型调研

> 项目目标：游戏创建平台，核心玩法为「玩家用手机/电脑摄像头做动作，实时驱动游戏中的角色模型」。
> 调研日期：2026-08-08

## 一、需求拆解

```
摄像头画面 → 姿态识别(人体关键点) → 骨骼重定向(重映射到游戏角色骨架) → 角色模型驱动(实时渲染)
```

关键约束：
- **跨端**：手机 + 电脑都要能用（浏览器 / 客户端 / 原生 App 三选一或组合）
- **实时性**：目标 30 FPS 以上，延迟 < 150ms 才有游戏可用性
- **平台化**：是一个"游戏创建平台"，意味着创作者要能在平台上做游戏，玩家直接玩——**分发与部署方式**对路线选择影响很大
- **精度预期**：全身动作为主（跑、跳、挥手、踢腿等行为识别），手指级精度通常非必需

## 二、参考项目剖析

### 1. MetU（GanniPiece/MetU）— MediaPipe 骨架 → Unity Humanoid
- **定位**：把 MediaPipe 识别出的骨架映射到 Unity 人类骨骼的参考实现
- **技术栈**：Unity 2021.3 + MediaPipe 0.8.10（通过 homuler/MediaPipeUnityPlugin 集成，含 Docker/WebGL 构建脚本）
- **核心价值**：解决了「MediaPipe 33 关键点 → Unity Humanoid 骨骼」的坐标系转换与映射问题（按全局坐标映射，而非局部 IK），提供可直接参考的映射代码
- **现状**：MIT 协议开源，2023 年 3 月后停止更新，12 个 commit，属学习/参考型项目，不建议直接作为平台底座
- **对我们的意义**：骨架映射层（2D 关键点 → 游戏骨骼）的核心算法参考

### 2. ThreeDPoseTracker（digital-standard）— 自监督 3D 关键点
- **定位**：纯摄像头实时 3D 姿态估计 + 驱动 VRM/FBX 模型的完整应用
- **技术栈**：Unity + Barracuda（神经网络推理引擎），VNect 风格模型
- **核心原理**：不是 2D 关键点 + 深度，而是**直接回归 3D 关键点**（24 关节，热力图 heatmap + 偏移量 offset 精修），规避了 2D→3D 深度歧义问题
- **后处理**：三层滤波（FIR + Kalman + 低通链），输出稳定平滑
- **输出能力**：驱动 VRM/FBX 模型、录制 BVH 动捕数据、通过 VMC 协议（OSC）把骨骼数据发给外部应用（如 VSeeFace、Unity 其他工程）
- **性能**：224×224（低清）/ 448×448（高清）两档，目标 30 FPS
- **现状**：开源，但模型训练数据与训练脚本不完整，依赖 Unity Barracuda（已停止官方维护，社区 fork 可用）
- **对我们的意义**：3D 关键点方案 + VMC 协议生态 + BVH 输出的完整参考

### 3. VSeeFace — 免费 VTuber 动捕软件
- **定位**：免费（可商用需看条款）的虚拟形象驱动软件，摄像头驱动 VRM 模型
- **技术渊源**：早期基于 ThreeDPoseTracker 算法改进，后独立迭代，是 ThreeDPoseTracker 思路在真实产品中的验证
- **能力**：面部追踪（表情、眨眼、唇形同步）成熟度高；全身追踪需配合 iPhone TrueDepth（通过 VMC 接收）或额外硬件；支持 OBS 串流
- **对我们的意义**：验证了「单摄像头 + VRM + 3D 关键点」路线的产品可行性；同时说明**全身高精度动捕单靠普通摄像头是瓶颈**，真实产品普遍用 ARKit/硬件补充

### 4. MediaPipe Pose / BlazePose
- **定位**：Google 开源人体姿态估计，官方跨平台方案
- **能力**：33 个关键点，同时输出 2D（像素坐标）与 3D（GHUM 统计人体模型拟合，米制坐标，原点在髋部中心）
- **平台**：Python / Web(JS) / Android / iOS 全覆盖；2023 年后官方推荐 **MediaPipe Tasks API（Pose Landmarker）**，旧版 Solutions API 已废弃
- **性能**：lite / full / heavy 三档，full 在手机端可达 30 FPS+，Web 端（WASM + GPU）也可实时
- **局限**：3D 是"单目深度估计"结果，侧身、前后遮挡时深度有歧义，手指无追踪（需另接 Hand Landmarker）
- **对我们的意义**：**跨端最省事**的姿态识别底座，社区案例丰富（如 kalidoface 用 BlazePose+FaceMesh+HandPose 在浏览器里驱动 VRM 模型）

## 三、三条技术路线（详细）

### 路线 A：Web 全栈（推荐优先验证）
> 浏览器即玩：`MediaPipe Pose Landmarker (JS) + Three.js + 骨骼重定向/IK`

- **链路**：WebRTC 摄像头 → Pose Landmarker 33 关键点（2D+Z）→ 关键点重定向到角色骨架（每帧求关节旋转）→ Three.js 渲染驱动
- **参考**：kalidoface 3D 动捕 demo、MetU 的映射思路（搬到 JS）
- **优点**
  - 零安装，PC/手机/平板浏览器直接打开即玩，天然契合"游戏创建平台"的**网页分发**模型
  - 前后端同构（Node/TS），编辑器、游戏、玩家端一套技术栈
  - 社区与教程最多，出原型最快
- **缺点**
  - 单目 2D→3D 深度歧义：侧身、转身、遮挡时关节跳动
  - 无手指追踪（可叠加 Hand Landmarker 补手部）
  - 手机浏览器性能受机型限制；WebGL 渲染复杂场景有压力
- **实现要点**：关节旋转用「关键点位置 → 向量夹角 → 四元数」重定向；对髋部/肩膀做低通或 One-Euro 滤波抗抖；角色模型推荐 GLB/VRM 格式（three-vrm 库可直接驱动）
- **预计进度**：MVP（单人模型 + 全身跟随）2~4 周；完整平台（编辑器 + 游戏模板 + 账号体系）2~3 个月

### 路线 B：Unity 引擎（效果上限最高，工程最重）
> 客户端型：`Unity + Barracuda 推理 VNect 自监督 3D 模型（或 MediaPipe Unity Plugin）+ Humanoid 驱动`

- **链路**：WebCamTexture 摄像头 → Barracuda 推理（VNect 3D 关键点，24 关节）或 MediaPipe Unity Plugin → 全局坐标映射到 Humanoid 骨架 → Animator 驱动
- **参考**：ThreeDPoseTracker（Barracuda + VNect 模型）、MetU（MediaPipe Unity Plugin + 骨架映射）
- **优点**
  - **直接回归 3D 关键点，无深度歧义**，腿部、转身、下蹲等动作明显比 BlazePose 稳定
  - Unity Humanoid 生态：VRM/FBX 模型直接可用，Animation Rigging 可做 IK 精细化
  - 可顺带产出 BVH 动捕文件、支持 VMC 协议对接外部生态
  - 游戏引擎能力全（物理、UI、多平台发布）
- **缺点**
  - 需安装客户端（桌面端）或打包手机 App，**分发门槛高**，与"网页即玩的创建平台"模型冲突
  - iOS/Android/WebGL 要分别处理；WebGL 打包后性能与加载体积不理想
  - Barracuda 已停止官方维护；ThreeDPoseTracker 的训练数据/脚本不完整，模型可商用性需自行确认
- **实现要点**：模型质量两档（224/448）；三层滤波（FIR+Kalman+低通）是稳定性的关键；骨架映射参考 MetU 的全局坐标方案
- **预计进度**：单人可玩版 1~2 个月；平台化（编辑器、创作者上传游戏、在线分发）需额外 2~3 个月，且需客户端或 WebGL 折中

### 路线 C：移动原生 + 深度传感器（AR 级精度，成本最高）
> 原生 App：`ARKit ARBodyTracking（iOS）/ ML Kit（Android）+ 深度摄像头 + 骨骼重定向`

- **链路**：手机摄像头（TrueDepth/ToF）→ 系统级 3D 人体骨架（ARKit 21 关节，含旋转与位置）→ 重定向 → 原生引擎渲染或串流给游戏
- **优点**
  - ARBodyTracking 输出的 3D 骨架**自带骨骼旋转、极稳定**，遮挡/转身鲁棒性好，支持手部（Hands ARKit 4+）
  - 原生性能最好，可支撑复杂游戏画面；iPhone 上 TrueDepth 还能做人脸表情捕捉
- **缺点**
  - iOS / Android 两套原生实现，开发量最大
  - PC 端无此能力，需另配路线 A/B，形成多端分裂
  - 用户需下载 App，"即开即玩"体验最差；深度传感器非所有机型都有（安卓碎片化严重）
- **变体思路**：不做原生游戏，只做「原生动捕 App 通过 VMC/网络协议把骨骼数据串流给 Web/Unity 游戏」——兼顾精度与平台化，但增加一层设备依赖
- **预计进度**：iOS 端动捕模块 2~3 周；全平台（含安卓 + PC 串流链路）2~3 个月

## 四、横向对比

| 维度 | A · Web 全栈 | B · Unity 引擎 | C · 移动原生 |
|---|---|---|---|
| 识别方案 | BlazePose 单目(2D+Z) | VNect/MediaPipe 3D 关键点 | ARKit/系统级 3D 骨架 |
| 全身精度 | 中（侧身/遮挡会跳） | 高（无深度歧义） | 最高（自带骨骼旋转） |
| 手部支持 | 弱（需叠加模型） | 中 | 强（ARKit Hands） |
| 跨端(手机+PC) | 全端浏览器即玩 | 需打包安装 | 双端原生，PC 另配 |
| 平台化(创建平台) | 最顺（网页分发） | 中（客户端/WebGL） | 最难（App 分发） |
| 实时性能 | 中（机型相关） | 高 | 最高 |
| 社区/教程 | 最多 | 中（参考项目较旧） | 中（官方文档好） |
| 典型周期(MVP) | 2~4 周 | 1~2 个月 | 2~3 周(iOS)/2~3 个月(全) |
| 推荐场景 | 快速验证玩法 | 追求动作效果 | 主打手机沉浸体验 |

## 五、选型建议

1. **先跑路线 A 验证玩法**：用 MediaPipe + Three.js 两周内做出"对着摄像头挥手，角色跟着动"的可玩 demo，验证动作识别体验是否符合预期——这个判断决定了整个平台的方向。
2. **效果不够再演进**：若 A 的动作抖动/侧身漂移不可接受，将识别层换成 ThreeDPoseTracker 式 3D 关键点模型（在 Web 端可用 ONNX Runtime Web 跑，或降级到路线 B）。
3. **平台架构保持"识别层可插拔"**：把「姿态识别 → 标准骨骼数据（如 BVH/VMC 格式）」与「游戏渲染」解耦，未来无论换成 ARKit 串流还是惯性动捕硬件，平台侧无需改动。
4. **长期进阶**（非 MVP 范围）：VRM 模型标准接入（three-vrm / UniVRM）、面部+手势补充识别、行为意图识别（姿态序列 → 游戏操作映射，如"举手=跳跃"）、可选 IMU 动捕硬件（Rokoko/Xsens）与光学动捕（Vicon/OptiTrack）的企业级支持。
